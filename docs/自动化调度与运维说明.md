# WaterEco 自动化调度与运维说明

> 适用仓库：`Tiger-HZ/WaterEco` ｜ 站点：https://tiger-hz.github.io/WaterEco/
> 最近更新：2026-09-20（改为**每天 2 次深度采集**模式）

---

## 一、采集策略：每天 2 次，每次做深做透

不再按小时跑，改为**每天 2 次深度采集 + 2 次专项深活**，把单次时间放宽、参数加深，
追求「深度、全面、高质量」而不是频次。时间均为北京时间。

| 任务 | 时间 | 做什么 | 单次上限 |
|---|---|---|---|
| **自动采集与部署**（auto.yml） | **每天 09:00、17:00** | 五路深度采集（国家政策库 8 页 / 学术 / 微信 / Crossref / EuropePMC）→ 配图回填 120 条 → 坏链自查 → 体积治理 → 合并归一化 → 部署 | 90 分钟 |
| **多站点采集与原文检查**（sites.yml） | **每天 11:00** | 逐栏目深翻页（生态环境部 5 栏目 + 浙江省生态环境厅 + 住建部 + 农业农村部，每栏目 10 页）→ 入库 → 原文巡检 → 原文审查 800 条 | 240 分钟 |
| **全库原文回填**（refill.yml） | **每天 12:30** | 存量条目分级回填原文（学术走 Unpaywall/Crossref/OpenAlex/DataCite；政府页走 PDF 附件→HTML 正文），单轮 **1000 条** | 200 分钟 |
| 大批量采集（bulk.yml） | **手动** | 需要一次性灌入大量条目时用 | 260 分钟 |

> 四者共用同一个并发组，避免同时改写 `kb/inbox.json` 造成数据互相覆盖，
> 因此**刻意错峰**：auto 在 09:00/17:00，中间插入 11:00 的 sites 与 12:30 的 refill。
> 每天总占用约 6~7 小时，其余时间空闲，不会互相挤占。

## 二、每次运行都会执行的质量闸门

1. **坏链自查（fix_bad_urls.py）** —— 自动识别并纠正四类坏链：
   编造的长哈希链接（`openstd…?hcno=` 空壳页）、繁体代理链（`big5.www.gov.cn/gate/big5/…`）、
   英文版链（`npc.gov.cn/englishnpc/…`）、站点首页占位链；可匹配的标准会自动换成
   生态环境部标准库的真实详情页（`std_index.json`，146 条）。
   找不到原文的一律标注「暂未收录原文」并写明去哪儿查，**不留看似可用的假链接**。
2. **原文内容校验（content_guard）** —— 四道判定：错误页/风控页特征词、最小长度、
   标题实词重合度、中文占比。不合格的拒绝入库并标记重取。
3. **原文审查（original_finder）** —— 条目若只是讯息/解读，自动检索被指向的原文，
   按「权威性 40% + 完整度 30% + 对应性 30%」择优；标题用《》点名的文档必须对应上，
   否则宁可判「未收录」也不凑数。必知必会条目优先。
4. **覆盖率统计（coverage.py）** —— 每次采集后重算 `kb/coverage.json`，
   严格口径 = 原文全文 ÷ 条目总数（**不采用**不可信的 `content_fetched` 标记）。
5. **仓库体积治理（prune_repo.py）** —— PDF 分级保留 + 总预算控制，
   确保仓库体积远离 GitHub Pages 的 1 GB 站点上限。

## 三、稳定性机制

| 机制 | 作用 |
|---|---|
| **safe_push.sh（v2）** | 推送被拒时自动重试；同步远端时**代码一律以远端为准**（不会用旧代码覆盖新改动），只保留本地刚生成的数据；**始终不阻断部署** —— 采集再卡，站点也照常重建 |
| **每步硬超时** | 每个爬虫 `timeout <秒>` + step 级 `timeout-minutes` 双层保险，单个爬虫卡死不会拖垮整条流水线 |
| **`if: always()`** | 合并 / 提交 / 上传产物 / 部署 —— 只要任务跑起来就必然重建并部署站点，杜绝「静默停更」 |
| **失败告警** | 失败自动开 Issue 通知；**成功时自动关闭该 Issue**（恢复即销警，不会一直收到失败邮件） |
| **心跳文件** | 每次运行更新 `last_run.txt`；站点「系统管理」页会显示上次采集时间，超过 26 小时未更新会高亮提醒 |

## 四、日常怎么看（3 个地方就够）

1. **站点 → 系统管理**：上次自动采集时间、原文覆盖率看板（严格/宽松口径、缺原文清单）。
2. **GitHub → Actions**：三条工作流的最近运行；绿勾=正常。
3. **GitHub → Issues**：当前开放的告警（正常应为 0 条）。

---

## 五、收到失败邮件时怎么办

1. 先看是哪个工作流、哪一步失败（邮件里点 “View workflow run”）。
2. 若是 `提交入库数据` 失败 —— 属于并发推送冲突，`safe_push.sh v2` 已能自动重试，**属历史问题**。
3. 若是 `上传站点产物` 失败 —— 多为仓库体积逼近上限，运行体积治理即可（已常态化）。
4. 若连续多次失败且 Issue 未自动关闭，把 Issue 链接发我，我来定位。

> 说明：`cancelled` 不是失败 —— 是同一时刻有另一个采集任务在跑，本次排队被后一次调度替换，
> 属于正常的错峰行为，不需要处理。
